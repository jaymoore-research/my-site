jaydata

A public, read-only MCP server over a synthetic oncology panel cohort.

The data is invented. No sample corresponds to a person, and nothing here is derived from patient records. The cohort is generated from a fixed seed, and every result the server returns carries a provenance line saying so.

What it is

Four tools over one table. A model connects, asks how large a biomarker-positive subgroup is, and gets a numerator, a denominator and a caveat about the assay. That is the whole surface.

It exists to be pointed at. Aggregate access to a cohort is the ordinary shape of a genomics tool call, and it is easier to reason about what such a server should refuse when the cohort behind it is invented and you can read every line of it.

The cohort

Samples 200
Tumour types Colorectal, gastric, lung adenocarcinoma, melanoma, multiple myeloma — 40 samples each
Panel SYN-panel-v2, 1.94 Mb coding footprint
Measurements tmb_per_mb, variants_pass, purity, mean_depth
Identifiers SYN-1007 and the like. Every identifier must match SYN-\d+ or the server refuses to start

The four tools

Four, because each one answers a question somebody actually asks, and because every tool definition is re-sent to the model on every turn for the rest of the session. A wide server is a standing tax on the context window.

cohort_summary
How many samples are there, and how do they split by tumour type?

The orientation question, and the only tool that returns anything without an argument. It returns counts and nothing identifying, so it tells you the shape of the cohort without naming anyone in it. Every count is published as it is, because the fixture is invented and there is nobody in it to disclose.

assay_results
What was recorded for one named sample?

One sample at a time, on purpose, and the caller must already know the identifier. A tool that took a list, or took no argument at all, would be an export tool, and an export tool is a different risk class from a lookup. No tool on this server returns the list of identifiers, so the individual-level route cannot be used to walk the cohort.

  • sample_id — sample identifier, e.g. SYN-1007
biomarker_prevalence
What fraction sits at or above a cut-off on one measurement?

This is the question the surface exists for, because the routine ask is not "give me the table" but "is the biomarker-positive subgroup large enough to be worth an analysis". It answers with a numerator, a denominator and a proportion, and with nothing else.

The marker is a closed vocabulary of four column names, so there is no free-text filter and no column that is not a parameter can be reached through it.

A prevalence from this tool is a panel-derived count on a synthetic cohort. TMB in particular is sensitive to panel footprint, tumour purity and sequencing depth, so check assay_qc before reading a TMB-high fraction as anything but a first pass.

  • marker — which measurement to threshold, one of the four
  • threshold — a sample counts as positive at or above this value. For tmb_per_mb the conventional TMB-high cut-off is 10
  • tumour_type — one tumour type, or omit for the whole cohort
assay_qc
Is the assay data good enough to trust the answer to that?

The caveat that has to travel with the number. A TMB-high fraction computed over samples with low tumour purity or thin coverage is a statement about the assay and not about the disease, so this returns median purity and median depth alongside the count of samples falling below each floor. The floors are quoted in the result, because a QC count is unreadable without them.

Counts only, and both floors are fixed in the server rather than passed in, so this cannot be turned into a filter that selects samples one at a time. They are a minimum purity of 0.30 and a minimum mean depth of 300.

  • tumour_type — one tumour type, or omit for the whole cohort

Provenance

Appended to every result from every tool, so the caveat travels with the number instead of sitting in a README nobody opens.

Synthetic fixture, 200 samples, SYN-panel-v2 (1.94 Mb coding footprint). Not patient data.

Quote it whenever you quote a number from this server.

What it will not do

There is no run_sql, no query parameter and no where clause anywhere in the four schemas, so the set of questions this server can be asked is finite and you can enumerate it. Anything outside the schema is rejected by validation before a tool body runs: 

Unknown tool: 'run_sql'
1 validation error for call[cohort_summary]: where — Unexpected keyword argument
1 validation error for call[biomarker_prevalence]: marker — Input should be
  'tmb_per_mb', 'variants_pass', 'purity' or 'mean_depth'

The fixture is loaded once into immutable rows, no code path opens anything for writing, and there is no disclosure floor: every count is given as it is, so a small stratum returns its true number rather than a null. That last one is only defensible because the cohort is invented. Point this pattern at real data and a cell-size floor is the first control to put back.

Connect

claude mcp add --transport http jaydata https://<deployment>/mcp

One endpoint, POST /mcp, Streamable HTTP, stateless, answering with a plain JSON body. No key and no OAuth. Any client that speaks Streamable HTTP takes the same URL.
